# RAGScope v2 结果诊断与 v3 改进判断

## 阅读范围

本分析依据本轮上传的完整最终报告、生成汇总表和361行Codex对话。生成表实际是39组结果，不是5,520条原始模型输出；本轮未取得本地最新v2源码、journal、全部训练样本和22MB错误账本。因此，下文把“报告支持的事实”“数学推导”“待验证原因”和“建议”分开。没有声称已经重跑用户电脑上的模型。

本轮用程序解析汇总表，确认39组计数相加为5,520，失败32。这个核对只证明汇总内部数量一致，不能代替回到journal的独立审计。

## 1. 总判断

v2完成了可信的实验基础，但未达到“整体问答性能已经升级”的目标。旧SQuAD的0.905/0.950是检索召回，新QASPER的约0.48是答案文字F1，不能直接相减；这不取消路由、LoRA、重排的真实负结果。

上一版方案也应调整：它把功能覆盖和大实验矩阵放得太靠前，把逐题机制诊断、评价校准、问题类型对应的实际动作和小样本收益门槛放得太晚。下一轮不能只让代理完成更多模块和更多测试，应该以“每个改动是否消除一个已经定位的错误”为推进依据。

## 3. 最重要的根因候选

### A. 评价不够全面，但不能用“换指标”掩盖差表现

答案F1会惩罚同义改写和多余解释。2B/4B/9B的文字长度、自由回答/yes-no类型、引用附加字段不同，可能改变文字F1。应先用同一处理规则重评旧答案，核验QASPER多参考和类型规则。

加入BERTScore可以容忍同义词，但“提高2%”和“下降2%”语义很接近却事实相反。需要分别检查关键事实、证据支持、引用和拒答。RAGChecker、ALCE和FActScore提供了逐事实/引用的设计参考；不是把这些库装上就获得真值。

报告的200条支持性proxy是分层样本，其中67条存在同模型偏差。98条“supported”不能直接除以200变成整个系统可信率，更不能把其余全部称为幻觉。必须保留抽样权重、UNKNOWN和人工未审核状态。

### B. 更大模型倒挂可能同时包含真实能力差异与协议不适配

三模型主矩阵输入相同，Oracle也倒挂，说明原因至少不完全在召回。候选包括模板、thinking输出、stop/EOS、量化/后端、严格schema、解码和篇幅偏好。

官方Qwen3.5-2B和9B当前给出的非思考文本采样建议不同。因此统一greedy有利于控制变量，但不能代表每个模型的最佳实用工作点。新方案保留统一协议对照，并另做各自建议配置的重复种子实验；不保证官方建议一定提高分数。

一个可核对的上界：按E2的9B/R2拒答precision≈0.3846、recall≈0.2778及18个不可答题反推，约5个正确拒答、8个可答题拒答。即使8个错误拒答都被修到满分，F1最多增加8/182≈0.044，仍小于它和2B的约0.150差距。该整数推断需要journal确认，但提示“拒答更多”并非充分解释。

另一个混杂：Oracle输入中位约305token，真实R2约2136token；所以Oracle改善不仅可能来自找到更多证据，也可能来自少噪声。需要Oracle加等长干扰的对照。

### C. 全库E8不一定只是检索算法失败，还可能缺少目标对象

QASPER问题针对特定论文的标题/摘要提出。若把“他们训练了多大的模型？”直接送进509篇论文的全库，并且没有选中论文或给题名，目标可能不唯一。

对话报告19/100找齐证据，这是值得优先解决的现象；但在未见E8题目和分母前，不能说81题全是算法漏检。要分成“已指定论文”“题目可识别对象”“对象歧义”三类。悄悄加gold题名会改变任务，不能拿改善后分数冒充同条件提升。

对真正有明确目标的全库问题，采用题名/摘要文档候选→文档内证据，同时保留全库块旁路。分别测文档召回、排序前证据、重排后证据和打包后证据。

### D. neighbor与重排的选择规则过于脆弱

R512 neighbor的dev完整集合覆盖从68/92到69/92；改善8题、退步7题，不是简单“只改变一题”。净增一题刚好超过0.01工程容差，而连续覆盖下降。它既不是可靠的普遍收益，也不证明所有neighbor无用。

先选核心证据再补邻块；比较任务保证双方证据，总结任务保证章节覆盖。在固定2048预算下先比较，再测试4096，不能把多给文字伪装成选择算法进步。

原BGE已经有512-token窗口处理，不能未经代码检查就说“长文都被截掉”。仍需检查窗口聚合的长度偏置、打分与映射、实际排序以及高分段落是否被扩展预算挤掉。新reranker只增加一个小模型对照，不堆多个。

### E. 路由学的是一个容易受代理指标和成本污染的目标

历史路由不是“这是事实、比较还是总结”，而是根据文字F1和成本选择BM25/Hybrid/重排。若差距小、标签偏多数类、成本来自不同CPU/GPU条件，复杂网络学会全选便宜方法不奇怪，但仍需标签台账验证。

问题类型分类更可解释，但只有它触发不同有效动作才有价值。先实现局部、比较、章节总结三条工作流；用正确或明确来源的任务标签查看策略收益；再用分类器，测错分损失和额外开销。

SLM/Transformer/LSTM/Laya应放在相同分类任务内比较，先保留规则和线性基线。没有“正确分类也能改善答案”的证据，就不再训练更复杂的router。

### F. LoRA更应查分布和监督，而不是增加轮数

对话提供的线索是：训练主要看干净Oracle和较短输入，测试看真实检索和更多干扰。这个分布差异与新增23次拒答相容，但尚未证明因果。

先拆分材料充分仍拒答、材料不足合理拒答；检查loss mask、EOS、目标截断、引用ID可见性和训练目标质量。`eval()`与缓存开启据对话已核验，不应再套用通用“忘开eval”答案。

重新训练应针对检索噪声与证据使用：包括真实检索、证据+干扰、少量Oracle和真正不足的材料。借鉴RAFT数据构造，不需要从零训练LLM，也不需要宣称复现整篇论文。最多两组小LoRA，checkpoint依据真实dev答案而非只依据loss。

延迟先比较输出token和结束原因，再查adapter未合并开销；PEFT合并可能改善执行效率，但不能保证修复本次3.62倍，也不能救一个质量更差的adapter。

## 4. v3执行优先级

1. 本地取证、旧答案重评分、新holdout封存。
2. 生成协议冒烟和24题多因素有限诊断，修复可验证包装问题。
3. 文档范围、检索漏斗、核心证据优先打包与一个新reranker对照。
4. 真正不同的局部/比较/总结工作流；工作流有效后才训练类型router。
5. LoRA监督/分布/速度诊断，满足门槛才进行最多两次小训练。
6. 冻结候选，旧默认与新方案在新H_QA上比较，并做真实在线测试。

共6,000次新增LLM请求上限，包含失败、裁判、预热和合成标签，不为凑满而调用。新方案不要求所有复杂模块都启用；能用更简单的流程取得同等或更好结果，也是有效改进。

## 5. 执行与权限

保留D盘和既有模型/环境。按照最新报告允许任意阶段必要GPU，但不碰不明任务、未知断点或系统驱动。原训练遵循USER_MANUAL_RESUME，结束不自动恢复。Goal自动选择普通选型并连续推进，不能规避额度、权限或虚构人工审核。

完整步骤、预算、测试和停止规则见同目录 `RAGScope_v3_Goal_Plan.md`。该任务书已经明确“执行完成”和“性能达标”是两种结果；没有通过性能门槛不能把任务完成包装成成功升级。
